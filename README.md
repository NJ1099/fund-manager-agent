## ⚠️ 모의투자 전용

- `config.EXECUTION_MODE = "paper"` 이고, 다른 값이면 `ExecutionDesk` 가 시작 자체를 거부합니다.
- **브로커 커넥터가 붙어 있지 않습니다.** 주문을 외부로 전송하는 코드 경로가 이 저장소에 없습니다.
- PM(LLM)은 텍스트만 출력합니다. 어떤 비중도 바꾸지 않고 어떤 주문도 만들지 않습니다.
  근거: 원문이 인용한 Alpha Arena에서 프런티어 LLM 6개 중 4개가 손실을 봤습니다.

실거래로 넘어가려면 브로커 커넥터, 리스크 한도, 감사 로그, 그리고 **해당 관할의 규제 검토**가
별도로 필요합니다. 이 코드는 그 준비가 되어 있지 않습니다.

## 설치 (Windows / PowerShell)

Windows 10 · Python 3.13 · pandas 3.0 조합에서 전 구간 검증했습니다
(`nautilus_trader` 는 `cp313-win_amd64` 프리빌드 wheel 이 있어 Rust 툴체인이 필요 없습니다).

```powershell
git clone https://github.com/NJ1099/fund-manager-agent.git
cd fund-manager-agent

# Kronos 레포 (모델 코드) — .gitignore 에 등록되어 있어 이 저장소와 별도로 관리됨
git clone https://github.com/shiyu-coder/Kronos.git

# 가상환경 권장
python -m venv .venv
.venv\Scripts\activate

# torch 는 CPU 빌드로 받는 편이 빠릅니다 (기본 인덱스는 CUDA 포함본이라 수 GB)
pip install --index-url https://download.pytorch.org/whl/cpu torch
pip install -r requirements.txt

# .env 설정 (선택 — Kronos 레포를 프로젝트 루트에 뒀다면 없어도 동작합니다)
copy .env.example .env
# .env 를 열어 필요하면 ANTHROPIC_API_KEY 채우기
```

첫 실행 때 HuggingFace에서 `NeoQuasar/Kronos-mini`(4.1M)와 토크나이저를 내려받습니다.
CPU에서 동작하며 10종목 스캔에 약 12초, 모델 로딩까지 포함한 첫 사이클은 약 35초 걸립니다.

> **로그가 깨져 보인다면**: 로그가 전부 한국어라 Windows 기본 콘솔(cp949)과 충돌합니다.
> `bot.py`·`server.py` 가 표준 출력을 UTF-8 로 되돌리지만, 터미널 자체가 cp949 면
> `chcp 65001` 을 먼저 실행하거나 Windows Terminal 을 쓰세요.

## 실행

```powershell
python bot.py once        # 한 사이클
python bot.py loop        # CYCLE_INTERVAL_SEC 간격 반복 (테스트용)
python bot.py schedule    # 매 영업일 16:05 ET (원문의 "16:00 타이머")

python server.py          # http://localhost:8787 대시보드
python build_snapshot.py out.html   # 서버 없이 열리는 단일 HTML 스냅샷

python scripts/backtest.py --dry-run                    # 몇 사이클 도는지 먼저 확인
python scripts/backtest.py --start 2026-01-01 --step 5  # 과거 리플레이

pytest -q                 # 테스트 (모델·네트워크 없이 수 초)
```

대시보드는 15초마다 `/api/state`를 폴링합니다. 상단 **사이클 실행** 버튼으로 즉시 한 사이클을
돌릴 수 있고, **PM 논평 받기 ($)** 버튼으로 현재 사이클의 LLM 논평만 새로 받을 수 있습니다.
서버는 기본적으로 `127.0.0.1` 에만 바인딩합니다 — 이 API 들에 인증이 없으므로,
다른 기기에서 열려면 `SERVER_HOST` 를 명시적으로 바꿔야 합니다.

| 엔드포인트 | 하는 일 | 비용 |
|---|---|---|
| `GET /api/state` | 저장된 상태 반환 (폴링용) | 0 |
| `POST /api/run-cycle` | 한 사이클 실행 | `PM_LLM_MODE` 에 따라 0 또는 1회 |
| `POST /api/pm-opinion` | 현재 사이클의 논평만 LLM 으로 다시 씀 | 1회 (사용자가 버튼을 눌렀을 때만) |

## PM 논평을 LLM으로 올리기 · 비용 제어

키가 없으면 결정론적 룰 기반 논평이 나갑니다(같은 입력이면 항상 같은 출력, 비용 0).
`.env`에 키를 넣으면 LLM이 논평을 씁니다 — 역할은 동일하게 **읽기 전용**입니다.

```
# .env
ANTHROPIC_API_KEY=sk-ant-...
PM_MODEL=claude-sonnet-4-6
PM_LLM_MODE=once
```

### 비용이 언제 나가는가

**LLM은 사이클이 실제로 실행될 때만 호출될 수 있습니다.** 대시보드를 새로고침하거나
15초 폴링이 도는 것은 저장된 `state.json` 을 읽을 뿐이라 **어떤 모드에서도 비용이 0**입니다.

그 위에 호출 정책을 `PM_LLM_MODE` 로 제어합니다.

| 값 | 동작 | 비용 |
|---|---|---|
| `once` (기본) | 최초 1회만 호출, 이후 사이클은 룰 기반 | 총 1회 |
| `on_change` | **이상 징후가 있는 사이클에만** — 게이트 발동, 최적화 후퇴, 데이터 결손,<br>`PM_ALERT_LOSS_PCT`(기본 -2%)보다 나쁜 손실 | 이상이 있었던 사이클 수만큼 |
| `always` | 매 사이클 | 사이클 수에 비례 |
| `never` | 키가 있어도 호출 안 함 | 0 |

`on_change` 는 **일상적인 리밸런싱 주문을 트리거로 치지 않습니다.** 거의 매 사이클 주문이
나오므로 그걸 기준으로 삼으면 `always` 와 같아져 비용이 전혀 절감되지 않기 때문입니다.

지금까지 실제로 나간 호출 수는 `state.json` 의 `llm_calls` 와 대시보드 PM 블록 하단에
표시됩니다. 룰 기반으로 나간 사이클은 출처에 사유가 함께 적힙니다
(예: `rules:최초 1회 완료 — 비용 절감`).

### 논평이 낡을 걱정은 없습니다

**논평은 캐시되지 않습니다.** LLM 을 부르지 않는 사이클에는 룰 기반 논평이 **그 사이클의
실제 데이터로 새로 생성**됩니다. 예전 논평을 다시 보여주는 경로는 코드에 없습니다.
자산·비중·주문·견해 같은 숫자는 애초에 LLM 과 무관하게 결정론적 코드가 계산합니다.

그래도 특정 사이클에 대해 LLM 분석을 보고 싶다면 대시보드 상단 **`PM 논평 받기 ($)`**
버튼을 누르세요. `POST /api/pm-opinion` 이 호출되어

- 시장 데이터를 다시 부르지 않고
- 주문을 만들지 않고
- 저장된 그 사이클의 state 로 논평만 새로 씁니다

따라서 화면의 숫자와 논평이 항상 같은 사이클을 가리킵니다. 버튼은 LLM 을 쓸 수 있고
현재 논평이 룰 기반일 때만 나타납니다.

> 🔐 이 워크스페이스 규칙대로: 키는 `.env`에만 두고 코드·설정 파일에 직접 쓰지 않습니다.
> `.env`는 `.gitignore`에 이미 등록되어 있습니다.
> **주의**: 키가 `.env` 가 아니라 **시스템 환경변수**에 있어도 `os.getenv` 가 읽어갑니다.
> 의도치 않은 호출을 완전히 막으려면 `PM_LLM_MODE=never` 로 두세요.

## 장부 · 게이트

**장부는 주식 수 + 현금으로 관리합니다.** 비중만 들고 있으면 정수 주식 반올림과
최소주문금액 때문에 장부와 실제 체결이 계속 어긋나고, 그 오차가 평가자산에 조용히 쌓입니다.
주식 수 장부에서는 총 노출이 100%를 넘는 일이 **구조적으로 불가능합니다** — 현금이 먼저
바닥나기 때문입니다. 거래비용도 현금에서 직접 빠지므로 모의 성과가 낙관 편향되지 않습니다.

집행 직전에 게이트 두 개를 통과합니다.

| 게이트 | 언제 작동하나 | 무엇을 하나 |
|---|---|---|
| 리스크 | 누적 낙폭 ≥ 20% 또는 직전 사이클 손실 ≥ 5% | 비중의 상대 구조는 유지한 채 전체 노출만 50%로 축소, 나머지는 현금 |
| 회전율 | 기존 포지션의 매도측 교체량 > 25% | 목표를 현재 비중 쪽으로 선형 보간해 여러 사이클에 나눠 이동 |

회전율은 **매도측**으로 잽니다. 현금에서 신규 편입하는 것은 교체가 아니라 배치이므로
회전으로 세지 않습니다 — 양측 합으로 재면 최초 편입이 늘 100%로 잡혀서, 아직 아무것도
사지 않은 포트폴리오가 영원히 현금에 묶입니다.

## 대시보드에서 보이는 것

- **에이전트 의견** — 이번 사이클에 대한 PM 논평
- **성과 추이** — 전략 vs SPY 매수 후 보유 자산 곡선(둘 다 100 기준), 샤프·최대낙폭·변동성·
  승률·평균 회전율·누적 거래비용, 게이트 발동 여부
- **주목 종목** — 워치리스트 전 종목의 순위, 5일 견해, `LONG`/`AVOID`, 확신도,
  상승경로 비율, 비중, 한 줄 코멘트
- **예측 경로** — Kronos 경로의 5·50·95 분위 팬차트
- **주문** — 생성된 `MarketOrder` (전부 `SIMULATED`), 건별 거래비용
- **진단** — 최적화 성공/후퇴 여부, 적용된 제약, 현금·보유 주식 수·실현 회전율,
  BL 사후 이동폭(견해가 얼마나 반영됐나), 데이터 결손

> 주목도는 `확신도 × |견해|` 라서 **하락 견해가 강한 종목도 1위로 올라옵니다.**
> 그런 종목은 편입 대상이 아니므로 `AVOID` 배지가 붙습니다.

## 확신도를 어떻게 읽어야 하나

확신도는 **워치리스트 안에서의 상대 순위**입니다. 절대적 예측 신뢰도가 아닙니다.
경로 표준편차가 작을수록 높게 나오며, 이는 "모델이 이 종목에 대해 일관된 그림을 갖고 있다"는
뜻이지 "맞다"는 뜻이 아닙니다.

원문 저자의 독립 검증에서 Kronos는 5분봉 비트코인 기준 Brier 0.189로,
무작위 걷기 베이스라인 0.188과 통계적으로 구분되지 않았습니다.
이 에이전트의 견해는 그 한계를 그대로 물려받습니다.

Black-Litterman이 안전판 역할을 합니다 — 확신도가 낮으면 사후 기대수익이 시장 균형 쪽으로
되돌아가고, 포트폴리오가 자동으로 벤치마크에 가까워집니다. 대시보드의 **BL 사후 이동**이
0에 가까우면 그 되돌림이 일어난 것입니다.

## 내 보유 종목 (실계좌 분석)

실제 증권사에서 산 종목을 넣으면 **봇과 같은 연구 데스크(Kronos)** 로 견해를 뽑고,
포트폴리오 진단(집중도·상관·변동성·통화 노출·손익)을 함께 보여줍니다.

> **봇의 모의 포트폴리오와 완전히 분리돼 있습니다.** 여기 넣은 종목은 어떤 목표비중에도
> 들어가지 않고, 어떤 주문도 만들지 않습니다. 파일도 별개입니다
> (`state/holdings.json` vs `state/state.json`).

### 넣는 방법 세 가지

| 방법 | 설명 |
|---|---|
| **종목 검색** | "삼성전자", "애플", "TIGER 미국나스닥100", "SPY" 처럼 한글·영문 모두 검색됩니다. 국내 종목의 코스피/코스닥 구분(`.KS`/`.KQ`)은 자동으로 붙습니다 |
| **증권사 연동** | 토스증권 · 한국투자증권 Open API 로 잔고를 그대로 가져옵니다 |
| **CSV 업로드** | 증권사에서 내려받은 잔고 파일. 컬럼 이름이 달라도 알아서 찾고, `cp949` 인코딩도 읽습니다 |

### 증권사 연동은 조회 전용입니다

`.env` 에 키를 넣으면 대시보드의 「가져오기」 버튼이 활성화됩니다.

```bash
# 토스증권 — https://developers.tossinvest.com 에서 신청
TOSS_CLIENT_ID=
TOSS_CLIENT_SECRET=

# 한국투자증권 — https://apiportal.koreainvestment.com 에서 신청
KIS_APP_KEY=
KIS_APP_SECRET=
KIS_ACCOUNT=12345678-01
```

**두 증권사 모두 주문 API 를 제공하지만 이 프로그램에는 그 경로가 없습니다.**
어댑터 인터페이스에 있는 메서드는 `fetch_holdings()` 하나뿐이고, 주문·정정·취소에
해당하는 이름은 코드 어디에도 없습니다 (`tests/test_brokers.py` 가 이를 고정합니다).
매매는 증권사 앱에서 하세요.

키는 `.env` 에만 두세요. 토큰은 메모리에만 유지되고 파일로 저장되지 않으며,
오류 메시지에 자격증명이 섞여 나가지 않는지도 테스트로 확인합니다.

### 분석이 알려주는 것

- **종목별 모델 견해** — 5거래일 기대수익과 확신도. 예측력은 검증되지 않았습니다
- **집중도** — 최대 비중, 유효 종목 수(10종목이어도 한 종목에 90%면 사실상 1종목)
- **상관** — 보유 종목이 같이 움직이는지. 상관이 높으면 종목 수는 분산이 아닙니다
- **변동성** — 포트폴리오 연변동성과 분산 효과(가중평균 대비 얼마나 낮은지)
- **통화 노출** — 환율에 얼마나 노출돼 있는지
- **손익** — 평단이 입력된 종목 기준. 없는 종목은 지어내지 않고 제외합니다

계산할 수 없는 값은 0 이 아니라 "—" 로 표시하고, 시세·환율을 못 받은 종목은
합산에서 빼고 화면에 따로 알려줍니다.

**분석은 「분석 실행」을 눌렀을 때만 돌아갑니다.** 대시보드의 15초 폴링은 저장된
결과를 읽을 뿐이라 추론이 일어나지 않습니다.

## 백테스트

라이브는 하루 한 사이클씩만 쌓입니다. 파라미터를 하나 바꿔서 나아졌는지 보려면 몇 달을
기다려야 하죠. 백테스트 하네스는 과거 데이터를 날짜별로 잘라 **같은 파이프라인**을 다시
돌립니다.

```powershell
python scripts/backtest.py --dry-run --start 2026-01-01 --step 5
python scripts/backtest.py --start 2026-01-01 --step 5
python scripts/backtest.py --step 20 --no-cache      # 추론 난수를 새로 뽑아 재확인
```

| 옵션 | 뜻 |
|---|---|
| `--start` / `--end` | 기준일 범위 (생략하면 데이터가 허용하는 전 구간) |
| `--step` | 리밸런싱 간격, **거래일** 단위 (5 = 주 1회, 20 = 월 1회) |
| `--period` | yfinance 다운로드 기간 (기본 `5y`) |
| `--equity` | 초기 자산 |
| `--no-cache` | 추론 캐시를 쓰지 않음 |
| `--dry-run` | 기준일과 예상 추론 횟수만 출력 |
| `--out` | 결과 JSON 경로 (기본 `reports/` 아래) |

### 두 가지 규율

**전략 로직을 복제하지 않습니다.** 선별·최적화·게이트는 `core/cycle.py::plan` 을 부릅니다 —
`bot.py` 가 부르는 바로 그 함수입니다. 하네스가 로직을 복제하면 두 코드가 갈라지고,
백테스트는 실제로 돌아가는 전략이 아닌 것을 측정하게 됩니다.

**미래를 보지 않습니다.** 매 시점 그 날짜까지만 잘라서 넘깁니다. 룩어헤드는 에러 없이
성과만 좋아지는 종류의 버그라서, "스코어러에 들어간 봉의 마지막 날짜 ≤ 기준일"을
테스트로 고정해 두었습니다 (`tests/test_backtest.py`).

### 추론 캐시

첫 실행은 (종목 × 사이클)만큼 Kronos 추론이 필요합니다 — 10종목 × 60사이클이면 CPU로
10분 남짓. 결과는 `state/infer_cache.jsonl` 에 쌓이므로, **추론 이후 단계**의 파라미터
(`TOP_K`, `MAX_TURNOVER`, 게이트 한도 …)만 바꿔 다시 돌리면 거의 즉시 끝납니다.

캐시 키에는 모델·룩백·예측길이·샘플수·온도·top_p 가 들어갑니다. 이 값들을 바꾸면 캐시가
자동으로 무효화됩니다 — 안 그러면 "파라미터를 바꿨는데 결과가 똑같다"는 침묵 버그가 됩니다.

Kronos 는 샘플링 모델이라 같은 입력에도 매번 다른 경로가 나옵니다. 캐시는 그 난수를
한 시점에 고정하는데, 이건 하류 파라미터 스윕에 오히려 필요한 성질입니다 — 고정하지 않으면
`TOP_K` 를 바꿔서 성과가 달라진 건지 난수가 달라진 건지 구분할 수 없습니다. 반대로 견해
자체의 안정성을 보고 싶을 때는 `--no-cache` 로 끄세요.

### 백테스트 숫자를 읽는 법

**상한이지 기대값이 아닙니다.** 아래 편향이 전부 성과를 좋은 쪽으로 밀어 올립니다.

- **슬리피지 없음** — 종가에 전량 체결된다고 가정합니다. 회전율이 높을수록 낙관 편향이 커집니다.
- **생존 편향** — 워치리스트가 '지금 존재하는' ETF 10종입니다. 과거 시점에 이 10종을 고를 수
  있었다는 보장은 없습니다.
- **수정주가** — 과거 가격이 배당·분할로 소급 조정돼 있어 당시 실제 호가와 다릅니다.
- **표본** — 사이클이 몇십 개인 백테스트의 샤프는 신뢰구간이 매우 넓습니다.

그래서 판단 기준은 절대 수익률이 아니라 **벤치마크(SPY 매수 후 보유) 대비**입니다. 같은
편향이 양쪽에 걸리지는 않지만(벤치마크는 거래를 안 하므로 슬리피지가 없습니다), 적어도
"이 파이프라인 전체가 존재할 가치가 있는가"에는 답할 수 있습니다.

## 알려진 한계

- 백테스트 성과와 실제 수익 능력은 다른 능력입니다 (Quantopian이 30만 사용자에게서 확인한 결론).
- 일 단위 사이클을 전제로 설계했습니다. 틱 단위로 가면 이 구조는 맞지 않습니다.
- yfinance는 무료 소스라 결측·지연이 있습니다. 결손이 생기면 대시보드에 `데이터 결손`으로
  표시되고, 해당 종목은 주문 없이 마지막 알려진 가격으로 평가만 됩니다.
- **거래비용은 반영되지만 슬리피지는 반영되지 않습니다.** 모의 체결은 시장가가 종가에 전량
  체결됐다고 가정하므로, 실제보다 유리한 체결입니다.
- 사이클당 하루치 종가 하나로 손익을 계산합니다. 장중 낙폭은 보이지 않으므로 최대낙폭이
  실제보다 작게 나옵니다.
- 미국 공휴일을 반영하지 않습니다. 휴장일에 도는 사이클은 직전 영업일 데이터로 돌고
  주문이 거의 나오지 않습니다.
